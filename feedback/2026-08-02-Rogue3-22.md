- **Kind:** defect
- **Impact:** My own candidate, caught by an independent critic and not by me or by any gate. #62

  introduced `linkTarget`, which calls `FileSystemInfo.LinkTarget` **once per entry, 190+ times,

  and it aborts `TemplateDrift` with `Stopped due to error` and no violation line. That is item 4's
  exact symptom, reintroduced by item 1's fix, inside the commit whose own comment block — three
  screens above the offending function — enumerates the seams it made total and does not include the
  function the same commit added.
- **Expected:** A commit that claims to have fixed a defect class has fixed it in the code it is
  itself adding. This is checkable, mechanically, by re-running the enumeration after the change.
- **Observed:** Two false claims, both in the same branch, both found by the same critic re-running
  the grep the commit message says was run:
  1. `linkTarget`, above.
  2. `sensedReadinessFiles (File.ReadAllText …)` appears three times on the `Verify` path, and
     `runEvidenceGraphEmission` catches, restores and **re-raises** — so an unreadable
     `readiness/evidence-graph.md` still aborted `Verify` with no line, while `.fsgg/agents.yml` in
     a *different* target next door had been guarded. The commit message also said "four more
     producers" and then enumerated five.
  Both are now total. The evidence-graph readers fall the way that rule's own doc comment already
  said an unreadable graph should — "has sensed NOTHING, which is the rule's own worst case rather
  than an IO error to rethrow at the caller" — a paragraph that predates this cycle and had simply

#### §4.4 The Run build target stalls while the exact command it wraps succeeds

- **Kind:** friction
- **Impact:** The documented route to launch the product hung with no diagnostic, and the host concluded the app would not start before finding another route.
- **Expected:** The launch target either starts the product or fails with a diagnostic.
- **Observed:** `./fake.sh build -t Run` produced no stdout for over six minutes; only MSBuild node processes were alive, no `Rogue3` process existed, and the log stayed at zero bytes until the attempt was killed. `build.fsx:277` shows the target is a one-line wrapper: `runProcess "Run" "dotnet" (sprintf "run --project src/%s" (singleSrcProject ()))`. Running that inner command directly — `dotnet run --project src/Rogue3` — **succeeds**: exit 0, `window-opened=true`, `first-frame-presented=true`, `renderer-mode=OpenGL`. So the stall is not in MSBuild or `dotnet run`; it is in the FAKE wrapper or its interaction with them, which is what makes the owner attribution supportable rather than assumed. The stall itself has no committed artifact and is not reproducible by a reader from the workspace; the discriminating comparison is.
- **Evidence:** command:dotnet run --project src/Rogue3; command:dotnet build src/Rogue3/Rogue3.fsproj -c Debug; file:build.fsx
- **Version:** .NET SDK 10.0.302; FAKE build script at `97a352a`
- **Owner:** Rogue3, `build.fsx` Run target and its FAKE process wrapper
- **Recurrence:** new
- **Avoidable cost:** roughly ten minutes on one stalled launch, killed and retried by another route
- **Disposition:** product fix

## §11 Falsifiable improvements

Routing note: four of five findings target FS-GG repositories, this repository's issue tracker is empty, and no cross-repo route has been established. These are recorded here only; where they get filed is an open decision, the same one `feedback/2026-08-01-Rogue3-11.md` §4.7 and the completion report §7 already raise.

- **Make the feedback validator's verdict unambiguous.** Print failures to stderr and end every run with one explicit `PASS`/`FAIL` line. Owner: FS-GG `fs-gg-feedback-report`, `scripts/feedback-tool.fsx`. Acceptance: a non-zero run prints a line containing `FAIL` on stdout and emits no failure text on stdout alone. Duplicate of `feedback/2026-08-01-Rogue3-12.md` §11; recorded as recurrence, not as a new proposal.
- **Give the host acceptance contract a worked reading of the result.** State that the exit code must be captured without a pipeline, with the idiom. Owner: FS-GG `work-roadmap`, `references/feedback-contract.md`. Acceptance: the contract contains an example capturing the validator's own status. Would have prevented §4.1.
- **Add a board-governance precondition.** Require at least one row naming the repository, or an explicit operator acknowledgement, before the loop proceeds; and surface the engine's stderr warning rather than only stdout and exit code. Owner: FS-GG `work-board`, runtime preconditions. Acceptance: on a board with zero rows for the repository, the skill stops naming the markdown-ledger alternative. Would have prevented §4.2.
- **Require each milestone to state whether the product was run.** One line in the per-milestone report contract: the artifact was launched and what was observed, or it was not and why. Owner: FS-GG `work-roadmap`, per-milestone brief. Acceptance: a milestone report containing neither statement is not accepted. Would have surfaced §4.3 at M0 rather than after M10.
- **Make the `Run` target fail loudly.** Owner: Rogue3, `build.fsx:277`. Acceptance: `./fake.sh build -t Run` either launches the product or exits non-zero with a diagnostic within a bounded window, given that `dotnet run --project src/Rogue3` succeeds.

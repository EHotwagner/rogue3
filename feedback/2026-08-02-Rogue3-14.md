## §2 What worked

`SelfTest`'s existing design made this a one-step change rather than a workflow rewrite, and two of
its properties are reusable well beyond this repository.

**It is hermetic by construction.** `build.fsx` carries no `#r` directive — only BCL `open`s — and
its `engineAssembly` binding is `lazy`, forced only by `EvidenceGraph`/`EvidenceAudit`. Fixtures are
planted under the system temp dir. So `SelfTest` needs neither `dotnet restore` nor an engine feed,
and the step could be placed *before* the `Restore` step, where it fails fastest and cannot be
blocked by a package-feed problem. A gate designed this way is cheap to require; one that needs the
full restore closure is not.

**One step both enforces and (partly) self-proves.** `runSelfTest` plants a violation for each check
and requires the check to report it, *and* asserts `TemplateDrift` and `GeneratedGuidanceCheck` are
clean on the checked-out tree. So a single CI step enforces two gates and, for the check *functions*,
proves they are still able to fail — the direct answer to #34's finding that a gate step can be a
no-op that writes a success log. The qualifier is load-bearing and was not in the first draft of this
report: §4.5 shows the self-proof does not extend to `runSelfTest`'s own bookkeeping, so "it proves
itself" is true of the checks and false of the harness.

A related property is worth keeping: the repo-clean assertions call the check functions **directly**
rather than going through the targets. That turns out to be strictly stronger than invoking
`-t TemplateDrift` would be — with the dispatch arm neutered and real drift present, the target exits
0 and `SelfTest` exits 1 (§4.5). A gate that tests the function rather than the command is harder to
empty.

Simulating the CI checkout with `git archive HEAD | tar -x` — tracked files only, exactly what
`actions/checkout` produces — was a cheap and decisive way to confirm the step does not depend on
untracked local state. Given #56, where tracked roll-ups are derived from a partly-untracked tree,
this is worth making routine for anything wired into CI.

## §3 What did not

No product code needed correcting; this cycle changed one CI configuration file. Three things went
wrong in the cycle itself, all caught before merge and all by controls rather than by luck.

**The first candidate was green and wrong.** `./fake.sh -t SelfTest` as a bare step passed every

step had to grow an output guard, and the residual had to be filed as #57.

**The first exclusion list was incomplete.** A claims critic on a different rubric found a third
mandated gate the comment never named (§4.4). An exclusion list that reads as exhaustive and is not
is the same overclaim the item exists to correct.

**The base moved underneath the cycle.** Sibling PR #54 merged mid-flight, closing #26 — one of the
two issues the exclusion list was anchored on — and changing `SelfTest` from 30 to 77 cases. Every
quantity had to be re-measured after a rebase, and one committed checkpoint had to be retracted
(§4.2).

The reusable observation is that all three were caught by *different* controls: mutation testing,
an independent claims rubric, and re-reading board state. None of the three would have caught the
other two.

#### §4.5 SelfTest cannot detect that its own failure counter was deleted: 7 of 23 mutants survive it

- **Kind:** defect
- **Impact:** The author's single mutant supported the item's acceptance criterion. An independent sweep showed the criterion is **not** met in general: `SelfTest` tracks its result in one mutable counter, so deleting the single line `failures <- failures + 1` makes it print every `FAIL` and still exit 0. Combined with a vacuous check, **two single-line edits leave both `-t SelfTest` and `dotnet test -c Release` green.** Two further mutants defeat the gate on a tree carrying *genuine* drift.
- **Expected:** #34 added `SelfTest` so that "a check that silently stopped checking fails here first"; the item's acceptance is that no `build.fsx` check can be made to pass unconditionally without CI going red.
- **Observed:** A fresh-context code critic with licence to mutation-test reported 16 killed / 7 survived over one-edit mutants. Independently re-derived here: `templateDriftViolations` → `[]` **plus** deletion of `failures <- failures + 1` gives `SelfTest: 77 case(s), 0 failure(s)`, true exit **0**, while printing 15 `FAIL` lines. `if failures > 0 then` → `if false then` behaves identically. Two survivors defeat the repo-clean assertions with real drift planted in `.agents/skills/fs-gg-ai/SKILL.md`: stubbing both assertions to `true`, and adding `if root = Directory.GetCurrentDirectory() then [] else` to `templateDriftViolations` — the latter leaves all fixture cases passing and exempts only the real repository. Three more neuter the target dispatch layer. Two of the seven are closed here from inside the workflow; the rest need a `build.fsx` fix and are filed as #57. **The critic's proposed remedy for the dispatch survivors was refuted by measurement:** with the dispatch arm neutered *and* real drift present, `./fake.sh -t TemplateDrift` exits 0 while `-t SelfTest` exits 1, so adding target steps would be a weaker duplicate, not extra coverage.

**The first version of the guard reproduced the defect it was closing.** It grepped the log for the `FAIL` line — an assertion on the *absence of a negative*, which is fail-open. An independent reviewer showed that renaming one `printf` label (`"  FAIL %s"` → `"  [fail] %s"`), a cosmetic edit nothing in the repository pins, re-greened the exact two-edit mutant with 15 failing cases still in the log. Confirmed here before accepting it. The guard was rewritten to assert a *positive* signal — ok-count must equal case-count — which reds on a relabel of either message, on a silenced failure counter, and on a zeroed case count (all three measured). This is the third time in this one cycle that a gate turned out not to check what it appeared to (#34's no-op step, #26's falsified output, and now the fix's own guard), which is itself the strongest evidence for #57.
- **Evidence:** command:on a git archive export of 09895b9 with templateDriftViolations returning the empty list and the line failures <- failures + 1 deleted, ./fake.sh -t SelfTest exits 0 printing SelfTest: 77 case(s), 0 failure(s) alongside 15 FAIL lines, while the workflow guard script over the same output exits 1 reporting 62 passing case(s) of 77; command:on that same mutated export with eprintfn "  FAIL %s" relabelled to "  [fail] %s", the FAIL-grep form of the guard exits 0 while the ok-count form exits 1; command:on an export of bfd1288 with the TemplateDrift dispatch arm replaced by writeLog target and real drift appended to .agents/skills/fs-gg-ai/SKILL.md, ./fake.sh -t TemplateDrift exits 0 while ./fake.sh -t SelfTest exits 1; issue:EHotwagner/rogue3#57
- **Version:** reproduced at bfd1288 and at 09895b9.
- **Owner:** EHotwagner/rogue3, `build.fsx` `runSelfTest`/`expect`.
- **Recurrence:** new; continues the #34 → #26 → #52 progression of gate steps that do not check what they appear to.
- **Avoidable cost:** none avoidable — this is the finding. It did require one workflow rewrite and one new issue after the change was already green in local verification.

## §6 Doc-versus-behavior contradictions

`build.fsx`'s help banner says `Verify` runs "the merge-gate audit (EvidenceGraph -> EvidenceAudit)
— the audit hard-blocks until every task is [X]", and presents `SelfTest` as the check to "Run
before trusting a green gate". `docs/product.md` §"`Verify` embeds the merge-gate audit" says the
audit "**hard-blocks until the feature is complete** (every task `[X]`)". Up to and including
`09895b9` no CI job executed any `build.fsx` target, so on a pull request all three descriptions
applied to a locally-run command only — the word "gate" carried an enforcement meaning the repository did not
implement, and "run it before trusting a green gate" described an act no PR performed.

This change narrows the contradiction without closing it: `SelfTest` now runs on every PR, `Verify`
still does not (§4.4). The remaining gap is that neither document says *where* a gate is enforced.
Owner: `docs/product.md` and `build.fsx`'s banner text.

A second, smaller one: the workflow is named `verify` and still does not invoke the `Verify` target.
The name now means "the PR gate" rather than "the `Verify` target", which is defensible but unstated.

## §7 Workarounds still in the tree

- `scripts/audit-binding-exceptions.json` gains **two** entries in this cycle, excusing the bindings that this cycle's own edit staled — the audits of cycles -11 and -12, both of which cite `verify.yml` (§4.3). It was one entry at `bfd1288`; rebasing onto `09895b9` brought #54's audit, which cites the same file, so the cost of the edit grew while the branch waited. Removal condition: #49 or #53 replacing the shared ledger with per-cycle files, or making citation staleness advisory for files an audit merely cites. Risk of permanence: the ledger grows monotonically — 75 entries before this cycle, 77 after — and each entry is a standing record that a merged audit no longer describes the tree it cites.
- The three gates named in §4.4 remain unenforced, with a comment in `verify.yml` as the only record of the omission and its blocking issue. Removal condition: #56 for `Verify` and for the performance gate's tracked-artifact churn, #49 for the validator corpus. Risk: the comment is the only place the omission is written down, so deleting it silently restores the original defect of an unstated gap.
- The ok-count/case-count cross-check in the `verify.yml` step is a workaround for #57 — `SelfTest`'s exit code is not trustworthy on its own. Removal condition: `runSelfTest` made fail-fast so no single deletion silences it. Two risks of permanence. First, it protects CI only: anyone running `./fake.sh -t SelfTest` locally — exactly what `build.fsx`'s banner tells the reader to do "before trusting a green gate" — still gets the untrustworthy exit code, so the workaround can mask how weak the harness is. Second, it is coupled to two `printf` formats in `build.fsx` that nothing pins. The coupling is deliberately fail-*closed* (a relabel reds the job rather than silently disarming it, §4.5), so the failure mode is a confusing red rather than a false green — but a future edit to those strings will red CI for a reason the editor will not expect, and the comment in `verify.yml` is the only place that connection is written down.

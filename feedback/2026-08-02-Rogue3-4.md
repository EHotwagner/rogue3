## §3 What did not

- **A bounded drain that satisfied the governance pins silently discarded the evidence.** The first fix kept `ReadToEndAsync` and merely timed out the `.Result` wait. It terminated correctly, and it also returned zero captured characters — the readiness log would have been empty precisely when a command misbehaved. A throwaway harness caught this; no test in the repo would have. The design was replaced with incremental collection.
- **The natural success path could not be exercised through the product's own window.** The product process ran but no window was reachable on this host, so "close the window, expect exit 0" was not available. Proving `runInteractive`'s exit-0 branch required a scratch copy of `build.fsx` pointed at `--scene-evidence` (§4.4).
- **A green `Verify` left the tree dirty.** Tracked evidence artifacts were rewritten and had to be reverted before they contaminated an unrelated PR (§4.6).
- **The first draft of this report mis-attributed a scaffold-shipped recipe as a workaround for this defect.** `docs/product.md`'s `setsid` launch recipe was read as an adaptation to the broken `Run` target. `git log -S setsid -- docs/product.md` returns one commit, `cd0028f`, the baseline scaffold: the recipe predates the defect report and exists to keep the viewer alive after a terminal closes. The claim was removed from §4.1, §6 and §7 before finalization.

## §4 Findings

#### §4.1 The generated `runProcess` drains redirected pipes with no bound, so any command that leaves a surviving grandchild stalls the build forever

- **Kind:** defect
- **Impact:** High for every product generated from the `fs-gg-ui` template. The stall is not specific to `Run`: `Restore`, `Build`, `Pack`, `Test`, `PerformanceIntent`, `PerformanceEvidence` and `PerformanceCriticRequest` all route through the same helper, so any of them can hang indefinitely on a command that has already succeeded.
- **Expected:** A build target that shells a command reports that command's outcome within a time governed by the command, and writes its readiness log.
- **Observed:** `runProcess` read the child's redirected streams with `ReadToEndAsync().Result`. A pipe reaches EOF when the last writer closes it, and every grandchild inherits the write handles. MSBuild spawns worker nodes as children of `dotnet run`/`dotnet build` with `/nodeReuse:true` and deliberately keeps them alive for the next build; they reparent to PID 1 and hold the inherited handles long after the command exits. Surviving nodes are listable with the cited `pgrep`; their fd 1 and fd 2 entries in the kernel process file-descriptor table resolve to pipe write ends, which is the half of the mechanism carried in prose rather than a locator, because the audit format rejects the absolute path such a locator requires. The console echo, the readiness log write and the exit-code check all sit after that read, which is why a target that finished produced no output and a zero-byte log. The fix collects both streams incrementally, waits on the process with the timeout overload — the no-argument `WaitForExit()` additionally waits for the readers to reach EOF, which is the same stall — and bounds the post-exit drain, reporting an abandoned drain rather than losing it.
- **Evidence:** command:git show 1f19809:build.fsx; command:pgrep -af nodeReuse:true; file:build.fsx; issue:EHotwagner/rogue3#14
- **Version:** Reproduced against template `FS.GG.UI.Template::0.25.1` via generator `FS.GG.SDD.Artifacts/0.32.0`, .NET SDK 10.0.302. Whether a later template release already changed `runProcess` was not checked; none was available here.
- **Owner:** FS.GG.Rendering, the `fs-gg-ui` template's `build.fsx` `runProcess` helper. The prior report attributed this to Rogue3's `build.fsx`; `.fsgg/scaffold-provenance.json` shows that file is a template `producedPath`, so the root cause is upstream and the local fix is a divergence from the template until it lands there.
- **Recurrence:** first seen `feedback/2026-08-02-Rogue3.md` §4.4 (symptom and owner attribution); `issue:EHotwagner/rogue3#14`. This cycle adds the mechanism, the blast radius beyond `Run`, and the upstream owner.
- **Avoidable cost:** Six-plus minutes of silent stall per invocation before this cycle, and two 300s reproduction timeouts during it — a stall has no cheaper reproduction than waiting for it.
- **Disposition:** product fix

#### §4.3 Governance pins five literal strings from inside `runProcess`'s body, so the expression that caused the deadlock had to survive the fix

- **Kind:** quality-gap
- **Impact:** Medium for anyone repairing generated build machinery. The pins assert implementation internals rather than observable behavior, so they constrain how a defect in that implementation may be fixed. `let output = stdout + stderr` had to remain textually intact across a rewrite of the code that produces both operands.
- **Expected:** A governance assertion protects a property — redirected output is captured as clean text, not binary — in a way that survives a correct reimplementation of the code producing it.
- **Observed:** The test `generated Verify redirected output is clean text` asserts the presence of five literals in `build.fsx`: `RedirectStandardOutput <- true`, `RedirectStandardError <- true`, `let output = stdout + stderr`, `tryWriteTextLog logPath output` and `printf "%s" output`. All five are single expressions inside `runProcess`. The test's stated intent is behavioral; the assertion is textual. The shipped fix folds the abandoned-drain notice into the `stderr` binding — which serves a real purpose, routing the notice into both the console echo and the readiness log through one path, and which was also the only shape that left the pinned line untouched.
- **Evidence:** file:tests/Rogue3.Tests/GovernanceTests.fs; file:build.fsx

#### §4.4 The `Run` target has no bounded launch mode, so its success path cannot be asserted by an agent

- **Kind:** capability-gap
- **Impact:** Medium. A windowed product launched through `Run` never exits on its own, so an automated caller has no supported way to answer "does the product still start?" — the very question this item exists to make answerable. Verifying the fix's own exit-0 branch required patching a scratch copy of `build.fsx` to pass `--scene-evidence`, because no supported invocation reaches that branch.
- **Expected:** A launch target usable from automation can be asked to start the product, confirm it came up, and stop, with an exit code that distinguishes "started and healthy" from "failed to start".
- **Observed:** `-t Run` waits for a process only a human can end. `runInteractive` has no readiness-signal wait: the watchdog added by this cycle kills the product and fails, so a healthy product and a wedged one both exit non-zero once the bound is reached. This is a stall guard, not a smoke test, and `FSGG_RUN_TIMEOUT_SECONDS` should not be read as one.
- **Evidence:** file:build.fsx; command:FSGG_RUN_TIMEOUT_SECONDS=15 ./fake.sh build -t Run
- **Version:** template `FS.GG.UI.Template::0.25.1`
- **Owner:** FS.GG.Rendering, the `fs-gg-ui` template's `Run` target.
- **Recurrence:** new. Loosely related to `issue:EHotwagner/rogue3#13`, which drives play-through through the in-process input seam and does not need this target.
- **Avoidable cost:** One scratch copy of `build.fsx` and an extra verification round.
- **Known unknown:** separately from the template gap, no product window was reachable on this host, so the manual close-the-window route was also unavailable. That host condition was not diagnosed and is not part of this finding.
- **Disposition:** issue

- **Kind:** defect
- **Impact:** High for the worker protocol. `Verify` exits 0 and leaves tracked files modified; a worker that trusted the green gate and committed everything would ship evidence drift inside an unrelated defect PR.
- **Expected:** A verification gate reports; it does not rewrite tracked artifacts as a side effect.

So running the now-working `Run` target before `Verify` perturbs a tracked artifact in a way the broken target never could, which makes `#26`'s acceptance condition harder to meet than when it was filed.

## §11 Falsifiable improvements

- **Bound every pipe drain in the template's `runProcess`.** Prevents §4.1. Owner: FS.GG.Rendering, `fs-gg-ui` template `build.fsx`. Acceptance: a command that exits promptly while a grandchild holds its inherited stdout/stderr handles causes the target to complete within a stated bound, report the command's real exit code, and write a readiness log containing every line the command produced before the drain was abandoned.
- **Assert the behavior, not the source text, in the redirected-output governance test.** Prevents §4.3. Owner: FS.GG.Rendering, `fs-gg-ui` template `GovernanceTests.fs`. Acceptance: the test fails when a target's readiness log contains binary padding or is not written, and passes for any implementation that writes clean text, with no literal from inside `runProcess`'s body in the assertion.
- **Give `Run` a bounded smoke-launch mode.** Prevents §4.4. Owner: FS.GG.Rendering, `fs-gg-ui` template `build.fsx`. Acceptance: one documented invocation starts the product, waits for a stated readiness signal, stops it, and exits 0 on success and non-zero with a diagnostic when the product fails to reach that signal — a distinct outcome from a watchdog expiry, which means "still running".
- **Make evidence regeneration refuse an incomplete checkout, and stop letting target logs move the sensed set.** Prevents §4.6. Owner: EHotwagner/rogue3, `build.fsx` `EvidenceGraph`, against `#26`. Acceptance: running the gate in a worktree either leaves tracked artifacts byte-identical or fails with a diagnostic naming the missing inputs; `git status` is clean after a green `Verify`, and running any subset of targets beforehand — including `Run` — does not change the result.

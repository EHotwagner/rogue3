## §2 What worked

**The issue arrived with the diagnosis already done, in three layers, each independently
checkable.** The body isolated the effect wiring as correct; comment 1 used the
keyboard-survives/pointer-dies asymmetry to eliminate one of two leads; comment 2 reduced the defect
to a single enum arm by enumerating every `Borderless`/`Fullscreen` occurrence in the product. Every
claim was re-verified in source before any code was written and every one held.

**The `.fsi` api-surface mirrors under `docs/api-surface/` made the "is this fixable here?" question
answerable in minutes.** Establishing that `InteractiveAppHost` has no surface-changed seam — the
fact that decides local-fix versus upstream-route — was two greps against tracked files, with no
package extraction and no network.

**The native-window tier was reachable by extending a test that already existed.**
`Viewer.runtimeCapability().PersistentWindow` was true here, and the `#1022` test already drove a
mode change through a real bounded window run. Extending it to cover the mitigation path cost one
extra two-frame run and no new launch path. This cycle did not open native coverage — `#1022` already
had — it widened it.

## §3 What did not

**The first green candidate was wrong in four ways and a critic found all four.** The implementation
was correct and the suite green, but: the regression test's own comment claimed an acceptance it
structurally could not deliver; the in-source justification named a code path (`the next launch`)
that does not exist here; a restored-`Borderless` player was left with a settings screen showing no
mode selected; and the upstream issue number appeared in no source file. Three were corrected by
editing comments and one by adding a third guard plus a test. None changed the core mitigation — the
code was right and the *claims about the code* were not.

**My mutation teeth-check gave false confidence.** Three single-edit mutants against the new test all
died, which I read as the test having teeth. It has teeth — but not the ones claimed. Every mutant
perturbed the *surface*, which the test is sensitive to; none perturbed the *display mode*, which the
test's title is about and which it cannot observe. See §4.4.

**The report itself then repeated that failure.** See §4.9.

**`Verify` went red on a digest the moment the cycle touched a source file**, as it does for every
cycle here, and CI still cannot see that class of failure. See §4.6.

## §4 Findings

#### §4.1 `ViewerWindowStartupState.WindowedFullscreen` lands the window half off screen and misroutes every pointer sample, while exclusive `Fullscreen` on the identical path works

- **Kind:** defect
- **Impact:** A shipped settings option bricked the game's entire pointer UI with no recovery but a restart. Every FS.GG.UI product offering a borderless-fullscreen mode on a multi-output host is exposed.
- **Expected:** `SkiaViewer.fsi` documents `WindowedFullscreen` as borderless coverage of the monitor work area, and documents the host as owner of both the presentation fit and the inverse pointer mapping. Selecting it should present correctly and keep controls clickable.
- **Observed:** The window lands half off screen and no button responds, while `Esc` continues to work. Product code takes the identical path for both modes and diverges in exactly one match arm. **The mechanism is INFERRED from that observation plus the contract text, not established:** the most economical explanation is that the host's notion of the output surface disagrees with the real one, which would make presentation offset AND invert every pointer sample through the wrong fit — one cause, both symptoms. No debugger was run inside the framework and no two-output reproduction was performed by this cycle; the symptoms are the issue author's.
- **Evidence:** issue:EHotwagner/rogue3#63; issue:FS-GG/FS.GG.Rendering#1196; file:docs/api-surface/SkiaViewer/SkiaViewer.fsi
- **Version:** reproduced against `FsGgUiVersion` `0.21.1`, the current pin. Not re-verified against a later release; none was available to this workspace.
- **Owner:** FS-GG/FS.GG.Rendering — `src/SkiaViewer`, the `WindowedFullscreen` work-area derivation.
- **Recurrence:** new; routed to FS-GG/FS.GG.Rendering#1196 under the routing decision closed as EHotwagner/rogue3#16.
- **Avoidable cost:** none in this cycle; the diagnosis arrived with the issue.
- **Disposition:** issue

#### §4.2 `InteractiveAppHost` exposes no surface-changed notification, so a mode-driven surface change cannot be mitigated in product code at all

- **Kind:** capability-gap
- **Impact:** Decides local-fix versus upstream-route for an entire class of defect. A product whose window misbehaves after a runtime mode change has no seam from which to react, so its only options are to stop offering the mode or to violate the documented transform ownership.
- **Expected:** A host owning both directions of a coordinate transform either always re-fits on a surface change, or notifies the product so it can. One of the two must hold for the contract to be complete.
- **Observed:** Neither is documented. `InteractiveAppHost`'s members are `Init`, `Update`, `View`, `Theme`, `MapKey`, `MapPointer`, `Tick`, `MapKeyChord`, `OnFrameMetrics`, `Diagnostics`; `View` receives the LOGICAL size. `CaptureOutputSize` is a `ViewerRunEffect` and `InitialOutputSize` a `ViewerRunEvidence` field — both belong to the bounded-run evidence workflow and neither is reachable from an interactive host.
- **Evidence:** file:docs/api-surface/Controls.Elmish/ControlsElmish.fsi; file:docs/api-surface/SkiaViewer/SkiaViewer.fsi; issue:FS-GG/FS.GG.Rendering#1196
- **Version:** `FsGgUiVersion` `0.21.1`.
- **Owner:** FS-GG/FS.GG.Rendering — `Controls.Elmish` `InteractiveAppHost`, and the `SkiaViewer` contract text assigning transform ownership.
- **Recurrence:** new. Adjacent to FS-GG/FS.GG.Rendering#1014, which settled *who owns* the transform; that no change-notification exists alongside it is an absence observed in the current `.fsi`, not a statement about what #1014 considered.
- **Avoidable cost:** none — established before any code was written, which is what stopped this cycle attempting a product-side re-fit.
- **Disposition:** issue

#### §4.3 Effect-emission assertions certified a setting that bricked the UI — already known upstream, and still the shape of the product's coverage

- **Kind:** quality-gap
- **Impact:** The suite reported per-mode coverage of exactly the surface that was broken. This is the mechanism by which a green suite and an unusable product coexisted.
- **Expected:** A test looping every display mode and asserting each one's host effects should fail when one of those modes makes the product unusable.
- **Observed:** The pre-existing loop asserts each mode emits `ApplyWindowOptions` and `ApplyLogicalCanvas` with the right size. Both assertions were correct throughout — the effect wiring was never the fault. An emission assertion cannot distinguish a request that works from one that bricks the window; it is coverage of the dispatch, not of the mode.
- **Evidence:** file:tests/Rogue3.Tests/BehaviorTests.fs; issue:FS-GG/FS.GG.Rendering#1022; issue:EHotwagner/rogue3#63
- **Version:** n/a — a test-design property, not a versioned defect.
- **Owner:** FS-GG/FS.GG.Rendering — `template/product-skills/fs-gg-testing/`.
- **Recurrence:** **not new as an observation.** FS-GG/FS.GG.Rendering#1022 — closed, and the issue whose test this cycle extended — already states it: *"Emission tests can therefore pass while windowed/borderless/fullscreen changes never reach the live native window."* EHotwagner/rogue3#63's acceptance restates it. What is new is only that the insight sat in two issue threads and never reached the testing skill, so the product's coverage still had this shape at `715bef9`. The finding is therefore a *skill-guidance* gap, not a new observation, and is filed as such.

## §2 What worked

**The issue arrived with the diagnosis already done, in three layers, each independently
checkable.** The body isolated the effect wiring as correct; comment 1 used the
keyboard-survives/pointer-dies asymmetry to eliminate one of two leads; comment 2 reduced the defect
to a single enum arm by enumerating every `Borderless`/`Fullscreen` occurrence in the product. Every
claim was re-verified in source before any code was written and every one held.

**The `.fsi` api-surface mirrors under `docs/api-surface/` made the "is this fixable here?" question
answerable in minutes.** Establishing that `InteractiveAppHost` has no surface-changed seam — the
fact that decides local-fix versus upstream-route — was two greps against tracked files, with no
package extraction and no network.

**The native-window tier was reachable by extending a test that already existed.**
`Viewer.runtimeCapability().PersistentWindow` was true here, and the `#1022` test already drove a
mode change through a real bounded window run. Extending it to cover the mitigation path cost one
extra two-frame run and no new launch path. This cycle did not open native coverage — `#1022` already
had — it widened it.

## §3 What did not

**The first green candidate was wrong in four ways and a critic found all four.** The implementation
was correct and the suite green, but: the regression test's own comment claimed an acceptance it
structurally could not deliver; the in-source justification named a code path (`the next launch`)
that does not exist here; a restored-`Borderless` player was left with a settings screen showing no
mode selected; and the upstream issue number appeared in no source file. Three were corrected by
editing comments and one by adding a third guard plus a test. None changed the core mitigation — the
code was right and the *claims about the code* were not.

**My mutation teeth-check gave false confidence.** Three single-edit mutants against the new test all
died, which I read as the test having teeth. It has teeth — but not the ones claimed. Every mutant
perturbed the *surface*, which the test is sensitive to; none perturbed the *display mode*, which the
test's title is about and which it cannot observe. See §4.4.

**The report itself then repeated that failure.** See §4.9.

**And then a mutation critic found the mitigation was incomplete, after the PR was open with both
CI checks green and two critics satisfied.** Three guards had been placed on the seam the issue
named and none on the seam it did not: the command line reaches the same window request by a
separate route, no test exercised `WindowOptions.fs`'s behaviour, and its startup default was the bricking
state. See §4.10 — it is the most important finding in this report, and it is the one no amount of
reading found.

**`Verify` went red on a digest the moment the cycle touched a source file**, as it does for every
cycle here, and CI still cannot see that class of failure. See §4.6.

#### §4.10 A mitigation guarded every seam the issue named and missed a second, untested producer of the same dangerous value

- **Kind:** defect
- **Impact:** The product shipped, and this PR claimed in source and in its description, that no display mode requests `WindowedFullscreen` — while `rogue3 --window-backend vulkan` requested it at launch. Five separate mutants over `WindowOptions.fs` survived a green 275-test suite. The work-board's own operator guidance launches this product with `--window-options-file`, so the trap was on a path in active use.
- **Expected:** A mitigation that claims a dangerous value is never requested has enumerated everything that can request it.
- **Observed:** `parseWindowBehavior` defaulted `Startup = "windowed-fullscreen"`, and `windowFlagSupplied` routes the launch onto the parsed request for any of six flags — five of which say nothing about startup state. The default was therefore consulted **only** in combination with an unrelated flag, which is the worst possible shape: invisible from the flag the operator typed, and never exercised by the no-flag path where it would have been noticed. No test exercised `WindowOptions.fs`'s behaviour at all — `GovernanceTests.fs` referenced it three times at `715bef9`, but only as a compile-order index and a source-text scan, neither of which calls a function in it. Two fixes were needed because neither covers the other: the default is now `normal`, and `toViewerLaunchRequest` maps `windowed-fullscreen` onto exclusive `Fullscreen` while `#1196` is open. The new test is exhaustive over the flag vocabulary rather than sampled, because a test naming the startup values would have missed a defect that lived in a default; it was written first and observed red.
- **Impact, concretely:** the `work-board` operator brief instructs every worker on this repository to launch the product with `--window-options-file` — one of the six flags. An options file that omitted `startup=` would have launched straight into the bricked mode, on the exact path the guidance recommends. The fix removes that at the root, so no skill change is needed once this merges; without the fix, the guidance and the defect were pointed at each other.

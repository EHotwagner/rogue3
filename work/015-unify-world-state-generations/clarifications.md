# Unify World State Generations Clarifications

## Source Specification
- work/015-unify-world-state-generations/spec.md

## Clarification Questions
- CQ-001 [AMB:AMB-001]: The item's acceptance permits either removing the legacy field or stating an invariant with a test that fails on disagreement. Which does `Obstacles` get?
- CQ-002 [AMB:AMB-002]: The legacy `Enemy` record's `Velocity` is written by shot knockback and read by no integrator and no renderer. Does it move onto `EnemyActor` or die with the record?
- CQ-003 [AMB:AMB-003]: `resolveShotCombat` today drops zero-hit-point entries from `Enemies` while leaving them in `M5Enemies`. With one list, when does a dead actor leave the model, and is the difference observable?
- CQ-004 [AMB:AMB-004]: Does the `state.static-obstacles` cost driver survive the removal of the field its `ScaleSource` names, or is it a duplicate of `state.m5-obstacles`?
- CQ-005 [AMB:AMB-005]: Do the surviving `M5Enemies`/`M5Obstacles`/`M5ShopSlots` lose their prefix in the same change?
- CQ-006: `Radius` and `ContactDamage` stop being per-instance fields and become functions of `Kind`. Test fixtures used them to build harmless or oversized enemies. What breaks, and how is it kept honest?
- CQ-007: The canonical determinism encoding necessarily changes, so no digest can witness "behaviour is unchanged". What evidence replaces it?
- CQ-008: How are the moved workload definition digests re-declared without laundering an unreviewed change?
- CQ-009: What stops a removal-shaped change from silently deleting the coverage that proved the removed code worked?

## Answers
- CA-001: A derivation, and the field goes. `Obstacles` stores nothing `M5Obstacles` does not already determine: at all four sites that maintain it (`Model.fs` 1457, 1584, 1689 and the boot value) it is written as the *identical* filter-and-map over `M5Obstacles` — grounded-blocking kinds, mapped to a 40x40 rect at the obstacle's position. It is a cache, and the only thing a cache can do that a function cannot is be stale. An invariant test is strictly weaker: it can fire only *after* a reducer forgets the refresh, and only in the states the test happens to construct. Collapsing the four copies into one named derivation makes staleness unrepresentable rather than detectable, which is what the item's "a reader picks the wrong one and nothing says so" complaint actually asks for.
- CA-002: It moves. `Velocity` is dead in the sense that nothing integrates it — `Entities.stepEnemy` advances an actor by `speed * direction`, never by a stored velocity, and `Render` never reads it — but it is not dead in the sense that nothing observes it: `M3CombatHealthCurrencyTests` asserts `Velocity.Vx > 0` after a shot, i.e. that knockback is *recorded*. Dropping the field would delete that assertion, and deleting a tested behaviour inside a refactor whose whole claim is "a player sees no change" is exactly the move that makes a refactor untrustworthy. So `Velocity` is carried onto `EnemyActor`, its unintegrated status is stated in a comment at the field, and "shot knockback is recorded and never applied" is filed at root cause as its own observation rather than resolved here. The same reasoning carries `HitFlashTicks`, which the same test file asserts and which no renderer reads.
- CA-003: It changes *when* within the step, and the difference is not observable. Today `resolveShotCombat` rebuilds `Enemies` from a `HitPoints > 0.0` filter, so a killed enemy vanishes from the legacy list at that moment while its actor survives in `M5Enemies` until `stepM5Entities` — which is precisely the §14.21 gap. With one list a killed actor stays at zero hit points until `stepM5Entities`'s existing cleanup folds `damageM5Enemy` over the zero-hit-point ids in id order. That cleanup is the only thing that rolls the drop, credits the kill, splits a grub and clears the room, so it must stay the sole remover: dropping dead actors inside `resolveShotCombat` would destroy the drop roll. Between those two points the only readers are `resolveBombs`, `resolveEnemyDamage` and `resolveCombat`'s death count, and every one already filters `HitPoints > 0.0` — the bomb map damages only live entries, the contact grid is built only from live entries, and `aliveBefore`/`aliveAfter` are both live-id sets, so an entry that lingers at zero is counted dead exactly once either way. The step order is fixed and unchanged: `stepInput |> resolveCombat |> stepM5Entities |> stepM6Presentation`. **Correction, established by an independent code critic after this answer was first written:** the analysis above holds for the SHOT path only. At `d8d0024` bomb-blast and black-heart-burst damage was written to the legacy `Enemies` list alone and reached `M5Enemies` through an `hpById` re-sync that ran AFTER `stepM5Entities`'s cleanup fold, so a bomb or burst kill was invisible to the cleanup for a whole fixed step: the corpse took one more AI turn, and its drop roll, kill credit and room clear landed a step late. With one list they land in the step the damage does. Measured on both builds for an identical Grub-and-bomb scenario: `d8d0024` credits the kill and clears the room on step 2, the candidate on step 1; the death cue count is one in both. This shifts the `DropRng` draw order whenever such a kill coincides with another draw in the same step, so it is a real behaviour change and not a preserved behaviour. It is the same defect class as §14.21 and is arguably the correct outcome, but it is DECLARED in AC-008 and guarded by its own test rather than left to be discovered. No test covered a bomb kill at all before this item — both existing bomb tests use enemies that survive the blast.
- CA-004: It survives, re-pointed. `state.m5-obstacles` counts *every* obstacle in the room including `Spikes`, which does not block movement; `state.static-obstacles` counts the AABBs the player's swept cast and the shot-wall filter actually iterate. Those are different numbers over the same population and both are real cost. What changes is that the driver stops naming a stored field and starts naming the derivation: `ScaleSource` becomes the blocking-movement projection of `M5Obstacles`, and `MaximumExpected` is re-declared from the value the candidate's own run emits. Retiring it would remove the only counter over the player-collider set at the exact moment that set stopped being a field anyone can see — the wrong direction.
- CA-005: No. The prefix is a naming wart once the older generation is gone, and this item's acceptance says nothing about names. Renaming reaches `src/Rogue3/Render.fs`, `src/Rogue3/EvidenceCommands.fs` and `src/Rogue3/GameplayVisualInventory.fs`, none of which is in this item's touch-set and all three of which prior audits bind — so the rename would break three further audit bindings and add three further excuse-ledger entries for zero behavioural gain, while the ledger is contended with `EHotwagner/rogue3#38`. Deferred with the reason recorded, not silently dropped.
- CA-006: `ContactDamage` is what breaks, not `Radius`. Every kind in `Entities.roster` has `ContactDamage >= 1`, so a fixture can no longer build a contact-harmless enemy by setting the field to `0`; it must instead place the actor out of contact range, which is `playerRadius + definition.Radius <= 13 + 22 = 35` units at worst. Every existing fixture that used `ContactDamage = 0` already places its enemy 67 units or more from the player's `vec2 640 360` start — the nearest is the bomb target in `M3CombatHealthCurrencyTests` at `player + vec2 30 0`, which needs the enemy's radius to stay under 17 and gets 12 from `Grub`. So fixture enemies are re-expressed as real roster kinds whose radius and contact damage are the ones the product ships, with hit points set through `{ Entities.spawn ... with HitPoints = ... }`. That is a strengthening: a fixture enemy becomes an enemy the game can actually produce, instead of a shape with a 64-unit radius and zero contact damage that no floor can spawn.
- CA-007: The suite, re-pointed rather than reduced, plus a mutation check. A model-to-model digest comparison across the change is impossible by construction, and a golden digest would only re-state that three fields left the record. What can witness "a player sees no change" is that every behavioural assertion the product already had — damage numbers, knockback, hit flash, contact re-tick, pierce budgets, bomb chain damage, friendly-fire immunity, black-heart burst damage, obstacle blocking, spike damage, drop rolls, kill accounting, room clear, descent clearing — still holds at the same numeric values against the surviving representation. That is why FR-009 forbids deleting an assertion instead of rewriting it, and why the 228 tests at `d8d0024` are a floor rather than a target. The code critic is additionally directed to mutation-test: revert one change at a time and confirm a test actually fails.
- CA-008: From the candidate's own run, with the reason stated. `definitionDigest` folds `Determinism.encode (workload.InitialState())` — reflective over the whole record — together with the intent policy string and the workload's fenced source text. Removing three model fields moves the first for every workload; changing `maximumExpectedScale` moves the second; changing the `maximum-content` fixture moves the third for that workload. Each new value is copied from the run that is simultaneously green on p95, p99, scene nodes, catch-up and *every exact cost-driver equality* — `MaximumExpected` is compared for equality, not as a ceiling, in `maximum-content` (`src/Rogue3/PerformanceEvidence.fs` line 1827) — so a fixture that quietly got smaller reds the run instead of passing under the old budget. A digest that moves for a reason not on that list is a signal to investigate, not to copy.
- CA-009: Three things, in order of strength. First, FR-009 makes 228 a floor and forbids deleting an assertion in place of rewriting it — the legacy shop tests in `M3CombatHealthCurrencyTests` and `M10AcceptanceDeterminismTests` scenario 11 are re-pointed at `InteractM5Shop`/`purchaseM5ShopSlot`, not dropped, even though `M5EntitiesBossRoomsTests` already covers the M5 shop. Second, two fixtures become *unfalsifiable* rather than merely broken if their writes are dropped without an M5 equivalent — the friendly-fire assertion in `M10AcceptanceDeterminismTests` and the slide-along-AABB assertion in `M2MovementShotTests` — and each is re-expressed so it can still fail. Third, the §14.21 closure gains a new regression test, so the item's headline claim is guarded by something that can go red.

## Decisions
- DEC-001 [AMB:AMB-001] [CQ-001] [CA-001]: `Model.Obstacles` is **removed**. One exported derivation, `Model.blockingObstacleRects`, replaces the four maintained copies; the three read sites (`stepInput`'s player sweep, the `shotWalls` filter and the `TotalWallQueries` accounting) call it, and no reducer assigns a cache. The invariant option permitted by the item's acceptance is explicitly declined, with the reason recorded here.
- DEC-002 [AMB:AMB-002] [CQ-002] [CA-002]: `Rogue3.Entities.EnemyActor` gains `Velocity: Vec2`, `LastContactTick: int option` and `HitFlashTicks: int`, initialised to `zero`, `None` and `0` by `Entities.spawn`. `Radius` and `ContactDamage` do **not** move: they are read from `Entities.definition actor.Kind`. `Velocity`'s unintegrated status is documented at the field and filed at root cause as a separate observation.
- DEC-003 [AMB:AMB-003] [CQ-003] [CA-003]: The single list keeps zero-hit-point actors until `stepM5Entities`'s cleanup removes them; `resolveShotCombat` updates hit points and stops dropping entries. The step order is unchanged. A regression test asserts that a shot which kills an enemy produces exactly one drop-roll and kill-credit and leaves no representation of the actor after the step.
- DEC-004 [AMB:AMB-004] [CQ-004] [CA-004]: `state.static-obstacles` survives with `ScaleSource` re-pointed at the blocking-movement projection of `Model.M5Obstacles` and `MaximumExpected` re-declared from the candidate's run. `state.m5-obstacles` keeps counting the whole obstacle list. Neither is retired.
- DEC-005 [AMB:AMB-005] [CQ-005] [CA-005]: The `M5` prefix stays. Recorded as a deferral with its reason — three audit-bound files outside the touch-set, and a contended excuse ledger — not as a non-issue.
- DEC-006 [CQ-006] [CA-006]: Fixture enemies become real roster kinds. `Grub` (radius 12, contact damage 1) is the default stand-in for the old `ContactDamage = 0` fixtures, whose positions already keep them outside `13 + 12 = 25` units of the player; hit points are set through `{ Entities.spawn ... with HitPoints = ... }`. The 30-actor `maximum-content` enemy fixture becomes the existing `maximumM5Enemies` roster alone, and the cost drivers it feeds are re-declared from the measured run rather than tuned to preserve an old number.
- DEC-007 [CQ-007] [CA-007]: Behaviour preservation is evidenced by the re-pointed suite at unchanged numeric values plus independent mutation-testing by the code critic, not by a digest. The changed canonical encoding is declared as an expected consequence in AC-008 rather than treated as a regression.
- DEC-008 [CQ-008] [CA-008]: Every moved workload definition digest is re-declared in both `src/Rogue3/PerformanceEvidence.fs` and `readiness/performance-intent.yml` from the value the candidate's green evidence run emits, with the three reasons it moved recorded in `evidence.yml` and the cycle report.
- DEC-009 [CQ-009] [CA-009]: The 228 tests at `d8d0024` are a floor. The legacy shop tests are re-pointed at the M5 shop; the friendly-fire and slide-along-AABB fixtures are re-expressed so each can still fail; and the §14.21 closure gains its own regression test.

## Accepted Deferrals
- DEF-001 [DEC-005]: Dropping the `M5` prefix from `M5Enemies`, `M5Obstacles` and `M5ShopSlots` is deferred out of this work item. Condition to lift: an item whose touch-set includes `src/Rogue3/Render.fs`, `src/Rogue3/EvidenceCommands.fs` and `src/Rogue3/GameplayVisualInventory.fs`.
- DEF-002 [DEC-002]: Making shot knockback move an enemy, and drawing the hit flash, are deferred. Both fields are carried unchanged and the observation is filed at root cause.
- DEF-003 [CQ-009]: Making the shop grant the item it charges for is deferred. `purchaseM5ShopSlot` debits and empties the offer without touching `PlayerItems`, and the pre-M5 reducer removed here was the only code that did — unreachable, with zero production dispatch sites. Closing it needs stat modifiers on `Entities.ItemDefinition`, which the item pedestal and the boss reward need too. Filed at root cause as `EHotwagner/rogue3#47`; the two shop tests carry a characterization assertion naming it so the gap is visible rather than merely absent. Two of the deleted assertions (`PlayerItems` contents, recomputed `PlayerStats.Damage`) could NOT be restated against the surviving reducer, which is the one place CA-009's rule was not met, and this deferral is that admission.

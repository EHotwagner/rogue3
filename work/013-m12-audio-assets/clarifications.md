# M12 Audio Assets Clarifications

## Source Specification
- work/013-m12-audio-assets/spec.md

## Clarification Questions
- CQ-001 [AMB:AMB-001]: Where does the single cue id declaration live, given the generator must read it without the FS.GG package graph and `AudioCues.fs` cannot be loaded standalone?
- CQ-002 [AMB:AMB-002]: How many `floor-<n>-theme` tracks does the declared set contain, and what stops a floor index outside that range from requesting an undeclared track?
- CQ-003 [AMB:AMB-003]: Are the generated WAV files committed to a repository with no LFS, or generated during the build?
- CQ-004 [AMB:AMB-004]: What predicate does the guard use for "resolves to a real asset"?
- CQ-005 [AMB:AMB-005]: What counts as proof of audibility at launch, given the host cannot record the machine's audio output?
- CQ-006 [AMB:AMB-006]: Does the guard live in the existing `M8AudioTests.fs` or in its own file?
- CQ-007: What is the complete requested id set, and how is it derived rather than hand-listed?
- CQ-008: Does this change touch a measured production performance route, and which digests move?

## Answers
- CA-001: `AudioCues.fs` cannot be the standalone home of the declaration for a consumer outside the compiled product. Its first lines are `open FS.GG.Audio.Core`, `open FS.GG.Audio.Host`, `open Rogue3.Geometry` and `open Rogue3.Model`, so anything that reads it — an `fsi` generator script in particular — must resolve four package references and the whole model compile order. A generator that cannot read the declaration re-lists the ids, which is the drift the milestone exists to prevent. A dependency-free module can be `#load`ed by `dotnet fsi` in one line and compiled into the product in the same line.
- CA-002: Six. The final floor is hard-coded in the product: `Model.fs:1900` (`model.FloorIndex=6 && model.M5Boss.IsSome`) and `Model.fs:2105`/`:2108` end the run in victory when the floor-6 boss dies, so a run reaches floors 1 through 6. But `AudioCues.fs`'s `track` builds `floor-{max 1 index}-theme` from an unbounded `int`, so "six" is a fact about the model, not about the cue map, and the two can drift. Clamping the family into the declared range removes the drift by construction instead of by belief.
- CA-003: Committed. The failure this milestone closes is "the assets were never there"; making audibility depend on a generation step that runs during or before the build reproduces it in a new form — a fresh clone that runs `dotnet build` and `dotnet run` must be audible with no extra command. A repository with no LFS can carry the set: 29 mono 16-bit files at 22050 Hz — sfx under a second, themes four seconds — is 2,311,678 bytes, against a 1.63 MiB pack at `059e993`. That roughly doubles the repository, which is a real cost and is stated rather than glossed; it buys a game that makes sound with no download step, no LFS and no licence. Opacity is the real objection to committed binaries, and it is answerable: put the synthesis in compiled product source, make the script a thin driver over it, and have the guard regenerate every asset in memory and compare bytes against the committed file. A reviewer then reads the synthesis, and the suite proves the committed bytes are what that code produces.
- CA-004: `File.Exists` is not enough and neither is `Some bytes`. The backend's own failure vocabulary distinguishes `Unresolved`, `NotWav`, `UnsupportedFormat(channels, bitsPerSample)`, `UnsupportedCodec(formatTag)` and `UploadRejected` (`FS.GG.Audio.Host.AssetDiagnostics.Failure`), so a zero-byte or non-PCM file is silent for a different reason and would satisfy a naive existence gate. `FS.GG.Audio.Host.Wav.tryParse` and the `Wav.FormatPcm` literal are public, so the guard can apply the same structural test the device backend applies.
- CA-005: The host has no route to the sound card and cannot assert "a human heard it". Three things are obtainable and together are strong: the shipped build launched exactly as a player launches it prints no `did not resolve to an asset` diagnostic; the backend constructed from the same `OpenAlBackend.create Rogue3.AudioCues.resolver` line reports `Backend.kindOf = DeviceBacked` rather than the `RecordOnly` substitution that would make any playback claim vacuous; and every declared id resolves to bytes the shipped parser accepts. What remains unproven — that the speaker moved — is disclosed rather than asserted.
- CA-006: Its own file. Every milestone since M2 has one, the roadmap row is a milestone obligation rather than an M8 refinement, and `M8AudioTests.fs` is about *what is requested* while this guard is about *what resolves*. Mixing them makes the M8 file fail for two unrelated reasons.
- CA-007: Eighteen sounds and eleven tracks, twenty-nine ids. The track count is the number an author is most likely to get wrong by hand, and this one did on the first pass: title, shop, boss, game-over and victory are five named tracks, and the parameterized `floor-<n>-theme` family adds six more, for eleven. The generator's own summary line caught it. Sounds: `shot-fire`, `shot-hit`, `enemy-death`, `player-hit`, `player-death`, `dodge-roll`, `bomb-explosion` (the seven `AudioEvent` cases); `pickup-coin`, `pickup-key`, `pickup-bomb`, `pickup-heart` (the `PickupKind` mapping, where `Coin1`/`Coin3` share one id, `HalfRedHeart`/`SoulHeart` share one, and `Nothing` has none); `item-pickup`; `door-lock`, `door-unlock`, `floor-descend`, `boss-intro`, `boss-phase`, `boss-death`. Tracks: `title-theme`, `floor-1-theme` … `floor-6-theme`, `shop-theme`, `boss-theme`, `game-over`, `victory`. A naive `grep -ohE '(sfx|SoundId|TrackId) "[a-z0-9-]+"'` over the file returns twenty-five entries, of which two — `SoundId "save"` and `TrackId "theme"` — are inside `//` doc comments and are not requested at all, and which misses the floor-theme family entirely because it is built by interpolation. That is exactly why the set is declared in source and scanned for drift rather than grepped.
- CA-008: No. This work item adds no model field, changes no reducer, renders nothing and alters no fixed-step behaviour. `Determinism.encode` sees no new state and the UI-route digests hash `Model.fs` and `Render.fs`, neither of which changes. Every authored workload and UI-route digest must therefore stay byte-identical, and any that moves is a signal to investigate rather than to re-derive.

## Decisions
- DEC-001 [AMB:AMB-001] [CQ-001] [CA-001]: The cue id set is declared once in a new dependency-free module `src/Rogue3/AudioCueIds.fs`, compiled first in `Rogue3.fsproj` (it references nothing, not even `Vec2`). It exports one named value per id, a `floorTheme : int -> string` for the parameterized family, and `sounds`/`tracks` lists built from those same values. `AudioCues.fs` builds every `SoundId`/`TrackId` from it and holds no cue id literal of its own; the generator `#load`s it; the guard test reads it. One declaration, three consumers, no second list anywhere.
- DEC-002 [AMB:AMB-002] [CQ-002] [CA-002]: The declared set contains six floor themes, and `AudioCueIds.floorTheme` clamps its argument into `[1, floorThemeCount]`. The family is therefore total: every `int`, reachable or not, maps to a declared track, and a seventh floor would reuse the sixth floor's loop rather than fall silent. A guard scenario evaluates `floorTheme` across a range spanning well beyond the reachable indices and asserts every result is declared, so extending the game past floor 6 without adding a theme is a deliberate reuse rather than a silent miss.
- DEC-003 [AMB:AMB-003] [CQ-003] [CA-003]: The WAV files are committed under `assets/audio/`. Synthesis lives in compiled product source, `src/Rogue3/AudioSynthesis.fs`, as a pure `string -> byte[]` over the BCL alone; `scripts/generate-audio-assets.fsx` is a thin driver that `#load`s the two modules and writes one file per declared id. The guard regenerates every asset in memory from the compiled synthesis and asserts the committed bytes are identical, so reproducibility is a test rather than a claim, and no `dotnet fsi` invocation is needed to check it.
- DEC-004 [AMB:AMB-004] [CQ-004] [CA-004]: "Resolves to a real asset" means: `Rogue3.AudioCues.resolver` returns `Some`, and `FS.GG.Audio.Host.Wav.tryParse` accepts those bytes with `FormatTag = Wav.FormatPcm`, `Channels = 1`, `BitsPerSample = 16` and a non-empty `Data` chunk. Mono is required rather than incidental: `OpenAlBackend` spatializes per source, and a stereo buffer plays centred whatever position it is given. The guard also asserts an id with no asset fails this predicate, so the predicate is shown to discriminate rather than assumed to.
- DEC-005 [AMB:AMB-005] [CQ-005] [CA-005]: Audibility evidence is three-part and its limit is disclosed. (1) The shipped build is launched with `dotnet run --project src/Rogue3`, a window opens, and its combined output is captured and committed; a single `FS.GG.Audio.Host: ... did not resolve` line fails the obligation. (2) A new product evidence command `--audio-asset-evidence` constructs the backend through the exact `OpenAlBackend.create Rogue3.AudioCues.resolver` expression `Program.fs` uses, reports `Backend.kindOf`, and reports per-id resolution and parse results for the whole declared set. (3) The guard test covers the set headlessly. That a speaker physically moved is not claimed.
- DEC-006 [AMB:AMB-006] [CQ-006] [CA-006]: The guard is `tests/Rogue3.Tests/M12AudioAssetTests.fs`, compiled after `M11PlayabilityLegibilityTests.fs`. `M8AudioTests.fs` is unchanged: it asserts what the product requests, and stays the reason a cue id exists at all.
- DEC-007 [CQ-007] [CA-007]: The drift guard is a source scan, not a grep: it reads `src/Rogue3/AudioCues.fs`, strips `//` comment text (the file's own doc comments contain two `SoundId`/`TrackId` literals that are not requested), collects every remaining `SoundId "..."`, `TrackId "..."` and `sfx "..."` literal, and asserts each is a value `AudioCueIds` exports. A cue added with an inline literal therefore reds the suite instead of shipping silent. The scan reads the source from the repository root resolved relative to the test assembly, and fails if it cannot find the file, so a moved file is a failure rather than a vacuous pass over zero literals.
- DEC-008 [CQ-008] [CA-008]: No digest is re-derived. Every authored workload and UI-route digest is asserted unchanged by the existing suite; if one moves, that is investigated as an unintended coupling rather than accepted and copied.
- DEC-009: Resolution probes two roots in order — the process working directory, then the directory the running assembly sits in (`AppContext.BaseDirectory`) — and the assets are copied to the build output by `Rogue3.fsproj` and `Rogue3.Tests.fsproj`. Without this the product is audible only when launched from the one directory the assets sit beside, and the guard would be asserting against the repository tree rather than against what the built product can reach. `AudioCues.assetRoot` keeps its value and meaning; only the search adds a second root.
- DEC-010: The synthesized assets are placeholders in fidelity, not in function, and this is recorded openly rather than left for a reviewer to discover: they are oscillator, envelope and noise constructions, deterministic and licence-free, chosen so that v1 ships audible. Replacing them with authored audio changes no id, no declaration and no guard, and is a content decision the roadmap can carry separately.

## Accepted Deferrals
- DEC-011: Replacing the synthesized placeholder assets with authored or licensed audio is deferred out of this work item as a content decision (DEC-010). It is recorded on the roadmap as its own row rather than left implicit, and it discharges nothing this milestone claims: the availability defect and its gate are closed here regardless of who authors the samples later.
